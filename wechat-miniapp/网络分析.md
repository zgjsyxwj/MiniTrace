# 微信小游戏网络请求与游戏协议分析

## 1. 范围与结论口径

本文分析 `wechat-miniapp` 中《世界 Online》微信小游戏发布包的静态网络行为，覆盖：

- `wx.request` HTTP/HTTPS 请求；
- `wx.downloadFile` 资源下载；
- 固定 URL、动态 URL 和 CDN 路径生成；
- WebSocket 连接、发送、接收、重连和心跳；
- 请求参数、响应处理；
- 旧 `ByteArray` 协议、protobuf 协议号和部分消息结构。

结论标记：

- **已确认**：可以从当前发布代码直接确定；
- **动态**：构造逻辑已确认，但最终值来自服务端响应或运行时状态；
- **未证实**：代码提供能力，但尚未找到当前业务实际调用；
- **待抓包**：必须运行小游戏并记录网络数据才能确认。

本文中的行号对应根目录格式化后的源码。重新执行格式化脚本可能导致行号变化，应同时使用函数名、模块名或关键字符串定位。原始 `.wxapkg`、解包副本和 `devtools-game` 镜像中的同一逻辑不重复计数。

## 4. `wx.request` 与 HTTP/HTTPS 请求

### 4.1 通用 GET 包装

位置：`main.js:577-611`，函数 `gg.webReqGet(base, params, success, fail)`。

请求行为：

```text
URL = base + encodeUriData(params)
method = GET
responseType = text
header = 未显式设置
```

参数编码：跳过值为 `undefined` 或函数的字段，其余键值通过 `encodeURIComponent` 加入 query。

响应处理：

1. `statusCode > 400` 进入失败分支；源码因此会把恰好 `400` 当作成功，这是当前实现的边界行为；
2. 优先 `JSON.parse(response.data)`；解析失败则保留文本；
3. 通过 `setTimeout(..., 0)` 异步调用成功回调；
4. 微信 API `fail` 分支把 `errMsg` 交给失败回调。

### 4.2 通用 POST 包装

位置：`main.js:612-646`，函数 `gg.webReqPost(url, data, success, fail)`。

```text
method = POST
body = data || ""
Content-Type = application/x-www-form-urlencoded
responseType = text
```

响应解析与状态判断和 GET 相同，包括 `statusCode > 400` 而非 `>= 400` 的边界。

### 4.4 Data Nexus 行为上报 header 和触发条件

行为上报的 header 包括：

- `Client-Time`；
- `Sign-Value`：由 body、`user_action_set_id`、`secret_key` 等混合计算；
- `Sign-Version: 1.0`；
- `content-type: text/plain;charset=UTF-8`。

默认并发数为 4。满足以下条件之一可触发发送：

- 队列数量达到 5；
- START_APP、REGISTER、PURCHASE 等实时行为；
- 主动 flush；
- 小游戏切到后台；
- SDK 定时检查。

### 4.5 Egret HTTP 桥

位置：`subpackages/libs/egret.wxgame.min.js:640-755`。

`egret.wxgame.WebHttpRequest.send` 在 URL 被判断为 HTTP/HTTPS 时调用：

```js
wx.request({ data, url, method, header, responseType })
```

字段来自业务层 `open`、`setRequestHeader` 和 `send`。仅 HTTP 200 派发 `COMPLETE`；其他状态或 API fail 派发 `IO_ERROR`。对象响应会先 `JSON.stringify`。

该桥是资源 GET helper 的底层实现，不能和上层资源请求重复算成两个接口。

### 4.6 XMLHttpRequest adapter

位置：`subpackages/libs/weapp-adapter.js:1800-1965`。

adapter 把 `XMLHttpRequest.send` 转成 `wx.request`：

- URL/method 来自 `open`；
- body 来自 `send`；
- 默认 header 为 `application/x-www-form-urlencoded`；
- `setRequestHeader` 可补充 header；
- HTTP status 不论是否 2xx 都会进入 adapter 的 success，再触发 `readystatechange/load/loadend`；
- API fail 根据 `errMsg` 分发 `abort` 或 `error`，最后触发 `loadend`。

当前业务代码没有找到显式 `new XMLHttpRequest`，因此这是**已打包能力，未证实实际触发**。

## 5. `wx.downloadFile`、资源缓存与 CDN

### 5.1 唯一直接 `wx.downloadFile` 调用

位置：`main.js:73-121`，下载函数接收：

```text
remoteUrl
localPath
事件派发器
成功回调
失败回调
进度回调
```

实际调用：

```js
wx.downloadFile({
  url: remoteUrl,
  filePath: USER_DATA_PATH + "/" + localPath
})
```

行为：

1. `statusCode >= 400` 时删除目标文件并进入失败链；
2. 成功后延迟读取/解码本地文件；
3. 若微信返回“存储空间达到上限”类错误，会遍历并清理用户目录；
4. 非 `v/` 资源在严重失败后弹窗并退出小游戏；
5. `v/` 资源交回上层重试链；
6. 返回的 `DownloadTask` 可注册 `onProgressUpdate`。

未设置自定义下载 header。

### 5.2 CDN 地址来源

`/version` 响应中的 `cdnUrl` 是主资源 CDN 来源，处理位置为 `main.js:4259-4266`：

1. 去掉尾部或内容中的 `index.html`；
2. 若包含逗号，则拆成 `go.cdn_url_list`；
3. 默认 `go.cdn_url` 取列表最后一项；
4. 单值直接写入 `go.cdn_url`。

当前发布代码没有硬编码完整主资源 CDN，因此具体 CDN 列表属于**待抓包/待保存版本响应**数据。

### 5.3 资源逻辑路径到真实路径

位置：`subpackages/main/main.min.js:46420-46610`，核心函数 `getRealUrl`。

处理规则概括：

1. 已是外部绝对 URL，且不属于当前 CDN 的路径，通常原样返回；
2. 已符合 `assets/<目录>/<32位十六进制哈希>.<扩展名>` 或 16 位哈希形式时通常保留；
3. 普通逻辑路径通过版本资源树 `urlHash` 改写为：

```text
assets/<hash 前两位>/<hash><原扩展名>
```

4. 哈希前缀 `ad` 有 `dirad` 特判；
5. 地图目录有单独路径替换；
6. 找不到 hash 时可能返回 `null`，随后进入资源失败链。

### 5.4 最终 URL 与多 CDN 回退

位置：`subpackages/main/main.min.js:100840-101035`，`ResLdr.load/getCdnUrl/setCdnFail`。

```text
if realUrl 包含 "://":
    finalUrl = realUrl
else:
    finalUrl = getCdnUrl(logicalUrl) + realUrl
```

ZIP 资源会把 `.json` 改写为 `.zip`。多 CDN 从列表末尾向前选择尚未在 `cdnFailMap[logicalUrl]` 标记失败的节点；失败后为当前逻辑资源记录 CDN 失败，再换节点重试。

资源初始化阶段最多重试 9 次。普通资源默认重试 2 次；CDN 数量超过 2 时，普通资源重试上限提高到 CDN 数量。全部失败后才通知业务层。

### 5.5 资源类型和响应解码

位置：`subpackages/main/main.min.js:46190-46410`。

| 类型 | 加载方式 | 结果 |
|---|---|---|
| 图片 | `egret.ImageLoader.load` | Texture |
| 声音 | `egret.Sound.load` | Sound |
| JSON | `egret.HttpRequest` GET / TEXT | JSON.parse 后的对象 |
| TEXT | `egret.HttpRequest` GET / TEXT，设置 `Content-Type:text/plain` | 字符串 |
| BINARY | `egret.HttpRequest` GET / ARRAY_BUFFER | ByteArray |
| ZIP | 下载 `.zip` 后走解压/缓存链 | 包内资源 |

游戏加载后，`main.js:4660-4695` 会替换 `GameGlobal.getTypeLdr/getTypeDcd`。ZIP、`/game_bg/` 或未命中排除前缀的资源会转入根下载器并落到微信用户目录；`/game_bg/` 使用包内启动资源，不走远程下载。当前排除列表初始为空，因此绝大多数普通资源会经过下载缓存覆盖。

## 7. WebSocket 连接

### 7.1 实际业务调用链

```text
业务 Proxy.sendProto(Message)
 → Service.sendProto
 → Connection.send
 → gg.encodeMsg
 → Socket.send
 → WebSocket.send(ArrayBuffer)
 → weapp-adapter
 → SocketTask.send({data})
```

主要证据：

- Proxy 汇聚：`main.min.js:36349-36381`；
- Service/Connection/Socket：`main.min.js:103616-103914`；
- 消息初始化：`main.min.js:110012-110031, 112009-112018`；
- 微信 adapter：`weapp-adapter.js:1981-2094`。

`Socket.connect(url)` 创建 `new WebSocket(url)` 并设置 `binaryType = "arraybuffer"`。adapter 要求 URL 以 `ws://` 或 `wss://` 开头，最终调用：

```js
wx.connectSocket({ url, protocols })
```

`SocketTask.onOpen/onClose/onError/onMessage` 被桥接为标准 WebSocket 风格事件。

### 7.2 登录服地址

启动版本响应中的 `host`、`port` 写入 `go.host/go.port`，登录时拼接：

```text
go.host + ":" + go.port
```

证据：`main.js:4252-4260`、`main.min.js:101481-101509`。

代码不会自动补 `ws://`，而 adapter 强制校验 scheme，所以服务端下发的 `host` 必须已经包含 `ws://` 或 `wss://`。当前静态包没有保存 `/version` 的真实响应，因此登录服主机名和端口属于待抓包数据。

源码的缺失校验是 `!go.host && !go.port`，只有两者同时为空才拦截；只缺一个字段仍会拼接无效 URL。

### 7.3 游戏服地址

登录服通过旧二进制命令获取线路：

- `LC_GAME_GET_AREA_AND_LINE = 5007`；
- 重登录时请求 `LC_RE_LOGIN_GET_LINE_LIST = 5019`，但异步等待 5007 响应。

每个 `LineServer` 响应字段按顺序为：

```text
id: short
name: string
sockUrl: string
wapSocketUrl: string
httpUrl: string
state: byte
stateStr: string
```

证据：`main.min.js:72349-72370, 102578-102611`。

选服地址：

```text
go.wsurl || selectedLine.sockUrl
```

证据：`main.min.js:116929-116973`。`go.wsurl` 在当前解包中只找到读取，没有找到静态赋值；常规地址可确认来自登录服下发的 `sockUrl`，`go.wsurl` 属于运行时覆盖入口。

### 7.4 生命周期

- **open**：底层标记 connected，逐层发布 `ON_CONNECT_CREATE`；按连接类型执行登录服或游戏服创建命令，成功后启动 ping；
- **close**：释放 WebSocket、清理标记并发布断线；远端 close 除 1000/1006 外会记录 code/reason；
- **error**：构造异常或 `onerror` 发布 `ON_CONNECT_ERROR`，随后统一转换成 `ON_CONNECT_LOST`；
- **message**：读取 `e.data`，解码后交给 Service 和消息管理器。

位置：`main.min.js:101228-101358, 103821-103891`。

`Service.isConnected()` 不仅检查底层连接状态，还要求距上次收到任何消息不超过 360000 ms（6 分钟）。

主动 `Socket.close()` 只在 `_connected=true` 时生效；尚处于 `_connecting` 时不会关闭，这是当前实现的生命周期边界。

### 7.5 登录服和游戏服握手

登录服首先发送旧命令 `LC_CHECKEDITION = 5000`，请求字段依次为：

```text
版本: short
构建号: int
渠道: short
语言: byte
固定字符串: "11"
命令值: byte
固定值: byte = 2
```

响应包含公告、新游戏 IP、布尔值和服务器时间，然后进入账号登录。位置：`main.min.js:102513-102570`。

微信自动登录随后发送 protobuf `C2S_WXMP_AUTOLOGIN = 20060`。成功后保存账号、session、登录设置并发布 `ON_ACCOUNT_LOGIN`。

游戏服握手使用：

- 首次进入：`CG_LOGIN_PLAYERCHECK = 1`；
- 有 session 的重连：`CG_LOGIN_ACTORENTER_AGAIN = 7`。

字段依次为：

```text
ukey: long
session: int
固定值: byte = 0
构建号: int
固定值: byte = 1
```

成功后保存新的 `reSessionID`。位置：`main.min.js:102671-102729`。

### 7.6 重连

登录服断线：

1. 正常切换游戏服时 `isClientClose` 直接返回；
2. 其他情况清登录缓存；
3. 最多立即重连 3 次；
4. 超限后提示登录服不可用。

游戏服断线：

1. 资源已加载时显示遮罩、隐藏界面并发角色登出事件；
2. 发布 `TRY_RECONNECT`；
3. 仅应用 active、当前不在重连、Service 不健康时执行；
4. `SELFKICK` 提示账号已在其他设备登录；
5. 游戏服重连上限为 5；
6. 正常重连重新执行外层登录流程，再按 reconnectId 直连游戏服。

位置：`main.min.js:101302-101579`。

## 8. 心跳与时间同步

### 8.1 当前主动心跳：旧 ByteArray 协议

| ID | 名称 | 请求体 | 响应体 |
|---:|---|---|---|
| 16001 | `CG_SYSTEM_HEART` | 空 | 空；更新 `lastPingTick` |
| 16021 | `CG_SYSTEM_TIME` | 空 | 一个旧格式 `long`，表示服务器毫秒时间 |

每次连接创建成功后立即同步时间和 ping。更新周期为 1 秒；时间同步间隔 30 秒；距上次心跳响应超过 10 秒时再次发送心跳。该逻辑只重发，不直接关闭 Socket。

证据：`main.min.js:116820-116889`。

### 8.2 protobuf 心跳：存在但未确认主动使用

protobuf 枚举和注册表还包含：

- `C2S_HEART_PUSH = 32600`；
- `S2C_HEART_PUSH = 32601`。

两者都是无字段空消息。客户端监听 32601，但处理函数为空；当前源码未找到构造并发送 32600 的调用，因此不能把它当作当前定时心跳。

证据：`protobuf-bundle.min.js:23893-23944, 36685-36686`、`main.min.js:80895-80896, 101713-101716`。

## 9. WebSocket 帧与消息编码

### 9.1 外层帧

位置：`main.min.js:110077-110102`。

```text
offset 0: uint16 totalLength = bodyLength + 4
offset 2: uint16 commandId
offset 4: body bytes
```

`DataView.setUint16/getUint16` 没有传 `littleEndian=true`，所以两个字段均为**大端序**。

边界行为：

- 不校验实际数据长度是否等于 `totalLength`；
- 不检查最小 4 字节；
- 不循环处理一个 WebSocket message 中的多包；
- 假设一次 WebSocket message 恰好承载一条游戏消息；
- `totalLength` 只有 16 位，但没有显式消息体上限检查；
- 收到字符串帧时先 UTF-8 编码成字节再尝试按游戏帧解析。

### 9.2 protobuf 与旧 ByteArray 分流

位置：`main.min.js:23025-23176`。

```text
if getProtobufCls(commandId) 有映射:
    发送：protobuf Class.encode(message).finish()
    接收：protobuf Class.decode(bytes)
else:
    使用 egret.ByteArray 旧字段流
```

是否走 protobuf 由 module 227 的 `_protobuf[id] -> class` 注册表决定，不能只凭命令 ID 数值范围判断。注册表位置：`main.min.js:80378-81203`。

旧字段编码支持：

- `byte`、`short`、`int`、`bool`；
- `long`：先写 high int，再写 low int；读取后构造 `new Long(low, high)`；
- `string`：先写 3 字节长度，再把每个 JavaScript UTF-16 code unit 写成 short；
- `bytes`：同样使用 3 字节长度前缀。

旧协议没有集中 schema，必须从每个请求构造和响应处理中的 `put*`/`get*` 顺序恢复字段。

### 9.3 压缩与加密

当前核心 Socket 发送链只拼 4 字节头和原始消息体，没有发现 gzip、deflate 或其他帧压缩，也没有发现传输加密。

代码中的 AES 用于 `loginStorage` 本地存储：key/iv 经 MD5 后，对 `egret.localStorage` 值加解密；它不在 Socket send/receive 链上。位置：`main.min.js:65400-65474`。

## 10. 接收、分发和异步响应

完整接收链：

```text
SocketTask.onMessage
 → adapter WebSocket.onmessage
 → Socket.onWSMessage(e.data)
 → Connection.onMessage
 → gg.decodeMsg
 → Service.onMsgReceive
 → gg.onMsg(Message)
 → getProtoName(commandId)
 → 业务 onProto handler
```

主要位置：`main.min.js:103675-103703, 103758-103763, 110095-110137`。

Service 每收到一包都会更新 `_recvTick`。消息管理器使用 `getProtoName(commandId)` 生成事件名，发送等待和业务订阅共用该事件系统。

源码中的前后台队列行为值得注意：

- `isActive=true` 时，收到的消息先放入 `_msgs`，每帧最多处理约 16 ms；
- `isActive=false` 时反而立即分发；
- Deactivate 时先排空已有队列。

`sendProtoAsync` 默认等待与请求相同 ID 的响应，也允许指定响应 ID，例如 5019 请求等待 5007。默认超时 10 秒。它先发送再注册响应 handler，极快响应理论上可能在 handler 注册前到达。位置：`main.min.js:31684-31715`。

## 13. HTTP、资源下载和游戏协议的边界

- `/version`、支付、Data Nexus 都是 HTTP(S)；
- CDN 图片、声音、JSON、文本、二进制和 ZIP 是资源请求，不属于游戏消息协议；
- 区服列表通过登录 WebSocket 的 5007/5019 获取，不是 HTTP；
- 当前已识别 protobuf 消息都放在 WebSocket 的 4 字节帧中；
- 没有发现业务 `wx.request` 使用 protobuf body、protobuf Content-Type 或 arraybuffer protobuf 响应；
- `newGameIp` 先由登录服二进制响应下发，代码对该地址做一次 HTTP GET，成功后再发送验证码 WebSocket 协议；
- `LineServer.httpUrl` 会被反序列化并保存，但当前已读代码没有证实它被 `wx.request` 使用。

## 14. 静态分析无法给出的最终值

当前包不能独立确定：

1. `/version` 在某次运行实际返回的 `host`、`port`、`cdnUrl`、`payApi`、`iosPayUrl`；
2. 登录服实际下发的 `sockUrl`、`wapSocketUrl`、`httpUrl`、`newGameIp`；
3. `go.wsurl` 的运行时注入来源和值；
4. 当前 CDN 完整资源清单、各文件可达性和 CDN 回退顺序；
5. 只有旧协议常量但尚未逐个追踪 `put*`/`get*` 的全部字段；
6. 只有 protobuf enum、没有注册或调用证据的命令是否在当前版本启用；
7. 微信 UI API 内部对分享图、游戏圈图片的实际请求 header 和缓存行为；
8. 服务器是否对某些消息执行额外压缩、签名或网关转换。

## 15. 动态验证建议

为了把静态清单补全为“实际运行请求列表”，建议一次完整运行至少记录：

1. 启动前清空或隔离小游戏缓存；
2. 保存 `/version` 请求和完整响应；
3. 保存所有 `wx.request` 的 URL、method、header、data、statusCode 和响应摘要；
4. 保存所有 `wx.downloadFile` 的最终 URL、localPath、状态码、大小和失败原因；
5. 保存 `wx.connectSocket` 的 URL、protocols、打开/关闭/错误事件；
6. 对每个 WebSocket message 记录时间、方向、帧长、命令 ID 和 body 十六进制；
7. 对 module 227 注册的命令尝试 protobuf decode；其余命令保留原始 body，并结合 `put*`/`get*` 调用恢复字段；
8. 覆盖首次登录、选服、角色进入、切图、背包、邮件、聊天、战斗、支付、前后台切换、断网重连；
9. 保存 CDN 失败和切换节点过程；
10. 将运行结果与本文静态表交叉核对，新增“已观察次数、实际 URL、样例状态码、样例协议方向”等列。

抓包和日志产物应保存在项目目录内，例如：

```text
wechat-miniapp/captures/<日期或场景>/
```

不要只依赖临时代理记录或远程缓存。
