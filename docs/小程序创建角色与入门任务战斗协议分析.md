# 小程序创建角色与入门任务、战斗协议分析

日期：2026-09-05。本文只使用保存在项目内的动态明文帧、小程序逆向代码和既有分析资料，不把消息名或单次时序直接当作已确认业务规则。

## 一、结论摘要

1. 创建角色使用二进制 WebSocket 消息 `10002 / CG_LOGIN_CREATEACTOR`。本次成功请求和响应均完整解析，`unparsedBytes=0`；请求角色名为“斯特特里古”，返回角色 ID 为 `2586841`。
2. 进入游戏后的正式会话共记录 101 个完整游戏帧：48 个请求、53 个响应。主游戏连接为 `0x44c4000bbd88`，记录器无致命错误且没有超时。
3. 一场本地战斗的已确认结算链为 `12502 request → 12533 push → 12502 response → 11004 request/response`。`12502` 返回结果 `2`，与小程序常量 `RESULT_RIGHT_WIN` 对齐；本次获得经验 `20`，未升级。
4. 入门主线在本次会话中按 `1105 → 1106 → 1107 → 1108 → 1109 → 1110 → 1125` 推进。每轮核心链为 `10518 寻路 → 14503 提交 → 14591 主线任务推送 → 14503 响应`，中间按需要出现 `14502 接取` 和 `14501 NPC 任务数据`。
5. 移动 `10504` 在本次会话中只有客户端上报，没有同号响应。切图使用 `10506`，请求目标原始地图 ID 为 `900`，响应给出运行时地图 ID `30680`、原始地图 ID `900`、位置 `(20,8)`。
6. Android 恢复版应把这些抓包用作字段语义和状态转换证据，再逐项核对 Android DEX/Smali。不能直接重放小程序帧，也不能把在线服临时地图 ID `30680` 写入本地存档规则。

## 二、范围、角色与证据边界

### 2.1 截图和角色关系

本次证据中出现过多个名称，必须区分：

- “浦卿”是创建页较早截图中的输入，不是本次实际提交值。
- “柯宜修”是此前旧角色，截图中等级 1、战力 3805，不属于本次动态会话的新建角色。
- “伯里尔理娜”是用户曾报告的随机名，不是最终提交并抓到的名字。
- 本次 `10002` 实际创建并抓取的角色是“斯特特里古”。创建响应显示等级 1；游戏内截图所示战力为 3773。

创建会话与进入游戏后的会话使用同一微信小游戏网络进程，但游戏内帧没有再次解码角色 ID，因此不能仅凭进程相同证明游戏内会话一定对应 `id=2586841`。文中只把两段证据按操作阶段连续整理，不把身份连续性提升为确认规则。

### 2.2 证据强度

| 等级 | 定义 | 本文用法 |
| --- | --- | --- |
| A | 动态帧完整解码，字段无剩余字节；或原始短帧可无歧义还原 | 写为“已确认”或“本次观察值” |

单次会话中的固定值，例如 `seed=4`、`monsterGroupId=261`、运行时地图 ID `30680`，只是本次观察值，不是跨角色、跨地图或跨版本的确认规则。

## 三、抓取方法与可信边界

微信小游戏实际网络进程是 `WeChatAppEx.exe` PID `27200` 的 Chromium `NetworkService`，流量经本机 Clash Verge `127.0.0.1:7897`。Winsock 层只能看到以 `17 03 03` 开头的 TLS 密文，因此最终在 `flue.dll` 的明文边界记录：

- 客户端写：`flue.dll+0x573550`
- 客户端读：`flue.dll+0x4C06990`

原抓取器位于来源工程，未迁入 Android 工程。正式游戏内记录窗口为 `2026-09-05T13:22:46.420Z` 至 `2026-09-05T13:24:04.655Z`。本项目只保留已筛选的游戏帧、解析结果和时间线。

`flue.dll` 是通用网络层，记录器还收到 27 个不能按游戏帧拆分的载荷。这些载荷全部来自 `0x44c4000b8608`、`0x44c4000b8308`、`0x44c4000b9808`，其内容包含 HTTP/1.1、HTTP/2、PNG、gzip、遥测或资源通信特征；它们不是主游戏连接 `0x44c4000bbd88` 上已确认的 ping、pong 或 close 帧。本文不把这些旁路载荷纳入游戏协议统计。

### 4.3 对 Android 恢复版的意义

恢复版保留创建页作为本地初始化入口。可以复用本次响应中的角色字段语义和经 Android 结构核对的外观样本，但名称、稳定 ID、默认值和持久化均由现有 Android 离线角色模块处理，禁止请求原服务器，也不复制未知的在线生成算法。

## 七、入门主线任务

### 7.1 业务主动链

本次任务间隔很短，且客户端存在自动任务代理。可以确认消息组成的业务主动链，但不能断言每个请求都由用户逐次手工点击：

`10518 寻路 → 14503 提交 → 14591 主线任务推送 → 14503 响应 → 14502 接取 → 14501 NPC 任务数据 → 下一次 10518`

第三次接取后没有紧邻 `14501`，切图后又并发出现两组 `14501`，因此上式是本次主循环概括，不是无条件固定协议顺序。

### 7.2 按任务阶段标注

| 1106 | `(13,21)` | `(5,1106,-1)` | 未确认非零奖励 | 接取 `(5,1107)` |

这里的 `1105～1110` 同时出现在 `10518` 的 short 和 `14503` 的第二个 short 中，并与主线推进一致；但现有构造器参数名不足以严格证明它在所有协议中都叫“任务 ID”。因此字段表保留“目标 short/第二个 short”的底层称呼，业务时间线才按任务编号描述。

1105 的 174 字节响应明显长于其他提交响应，其长奖励尾可能包含物品等复合字段；除已确认 MONEY3 变化外，准确物品字段仍未完成解码。

### 7.3 `10518` 任务寻路

六个请求均为 7 字节：`mode=2` 加一个 short。六个响应均为 8 字节：`result=0`、路径段数 `0`、最终坐标两个 byte。小程序 `createAutoMoveMsgByMisssion`、`onGotAutoPath` 和 `fromBytesByAutoMove` 与此结构对齐。

路径段数为 0 但存在终点，只能确认客户端获得了终点坐标；尚不能判断是同图直达、服务端省略路径还是客户端自行寻路。

### 7.4 `14503` 提交

构造器固定写 `short + short + int`，本次六个请求分别为：

- `(4,1105,-1)`，响应 174 字节
- `(5,1106,-1)`，响应 42 字节
- `(8,1107,-1)`，响应 53 字节
- `(1,1108,-1)`，响应 42 字节
- `(6,1109,-1)`，响应 42 字节
- `(12,1110,-1)`，响应 42 字节

六个响应均以结果 byte `0` 开始。小程序 `processMissionReward` 表明后续可能包含任务完成标记、NPC 状态、三类货币、经验与升级、宠物、背包物品及国家/城市字段，但普通 `14503` 的直接注册入口和每个动态尾字段尚未全部定位。除已列出的奖励外，不为零值或长尾强行命名。

### 7.5 `14502` 接取和 `14501` NPC 任务数据

`14502` 请求固定写两个 short，本次为 `(4,1106)`、`(5,1107)`、`(8,1108)`、`(1,1109)`、`(6,1110)`。五个响应均为 11 字节且首 byte 为 0，后续形式与 NPC 状态对相似，但末尾单 byte 未解释。

`14501` 请求由 NPC short、当前怪物组 ID 列表和当前怪物 ID 列表组成；响应由 `formatMissionData` 解析 NPC short、结果/任务数量、任务对象、怪物组及怪物数据。本次共 6 组请求和 6 个响应：

- 接取阶段四组：帧 `27/28`、`38/39`、`67/68`、`78/79`
- 切图后两请求并发：帧 `91/92`；随后响应为帧 `93/94`

切图后的协议中未确认请求关联键，`91→93`、`92→94` 只能按到达顺序暂配，证据强度为 D。

### 7.6 `14591` 主线任务推送

六次 `14503` 提交后均紧邻一次 `14591`，长度依次为 448、645、326、416、393、270 字节。静态常量和处理器明确它是 `GC_MAIN_LINE_TASK`：解析 Mission，更新 `MissionModel.mainMission` 和 `MainPlayerAi.curMissionId`，再按任务状态选择接取 NPC 或提交 NPC。

可以确认它是主线任务状态推送；“所有任务提交都必有一次 `14591`”只由本次主线样本支持，不能外推到支线、失败提交或重复提交。

## 八、移动、场景和切图

### 8.1 `10504` 移动

小程序 `createMoveMessage` 仅在目标变化时发送 x、y 两个 byte。本次五次客户端上报为：

`(22,21)`、`(22,19)`、`(15,21)`、`(13,13)`、`(6,17)`。

本次没有任何同号响应。这证明客户端把目标格单向上报，但不证明在线服务端从不做碰撞、节流、合法性检查或位置纠正。Android 恢复版应继续使用现有场景移动和碰撞判断，在合法移动完成后把最新格坐标写入本地存档，无需伪造 `10504` 响应。

### 8.2 `10506` 切图

请求帧 `000087-request-10506.bin` 的 SHA-256 为 `c57b979fec043ff656137fcdd971f1b57fe20fb4ec9a926fbc70f3c7123bf145`。原始字节与 `createJumpMapMessage` 对齐：

- `targetMapId(short)=900`
- `x=20`
- `y=8`
- `dataFlag=7232`
- boolean `false`

响应帧 `000088-response-10506.bin` 的 SHA-256 为 `5a436aa0ad479e4e237e85a927c48cb7da3a27d66ab4ce632ced33fe828fcb3a`，已确认头部字段：

- `result=0`
- 运行时 `mapId(int)=30680`
- 原始 `orgMapId(short)=900`
- 位置 `(20,8)`
- `dataFlag=7488`

小程序 `processDataBlockFlagMsg` 会按位继续解析角色、任务、背包、技能、其他玩家、地图、NPC、怪物等数据块。本次没有把 `7488` 对应的全部块逐字段导出，响应中出现的地图和 NPC 文本也不能替代正式地图配置。`900 → 30680` 只确认一个样本，运行时地图分配规则未知。

### 8.3 `10503` 世界数据

切图响应后，客户端发送 `10503`：当前运行时地图 short `30680`、boolean `true`、int `0`、两个零 byte。响应再次给出 `result=0`、运行时地图 `30680`、原始地图 `900`、位置 `(20,8)`、数据块标志 `0`。

这说明当前小程序版本同时存在运行时地图 ID 和原始地图 ID。本次抓到的 `900/30680` 只能作为双 ID 机制的证据，不得替代 Android 恢复版当前地图编号，也不能把 `30680` 写入跨重启的稳定存档。

### 8.4 `10505` 其他玩家状态

切图后每约 3 秒发送一次空请求，共 5 次，无响应。静态场景更新代码支持其轮询用途；但没有“其他玩家发生变化”的响应样本，因此返回布局未确认。Android 恢复版以单机可玩为范围，无需实现。

## 十、原 H5 本地版设计记录

本节保留来源分析当时的设计推导，只用于理解抓包可支持哪些本地状态。它不是 Android 恢复版方案；Android 实现必须复用现有角色、地图、任务和战斗模型，具体适配边界见 [小程序协议到 Android 离线适配.md](小程序协议到Android离线适配.md)。

### 10.1 总体状态机

首版最小状态可表达为：

`BOOT → LOAD_OR_INIT_PRESET_ROLE → LOAD_FIRST_MAP → SCENE_ACTIVE`

场景内分支：

- 移动：`SCENE_ACTIVE → LOCAL_MOVING → ASYNC_SAVE_POSITION → SCENE_ACTIVE`
- 任务：`AVAILABLE → ACTIVE → READY_TO_DELIVER → SETTLE_REWARD → COMPLETED/NEXT_AVAILABLE`
- 战斗：`SCENE_ACTIVE → LOCAL_BATTLE → VALIDATE_RESULT → SETTLE_REWARD → SCENE_ACTIVE`
- 存档失败：进入可重试的 `SAVE_FAILED`，但前端位置显示不回退到网络等待态

首版只有首图 16，不提供跨图传送，因此不实现 `10506` 状态分支。未来开放地图时再加入 `MAP_TRANSITION → LOAD_SCENE → SCENE_ACTIVE`。

### 10.2 最小持久化字段

| 模块 | 建议字段 | 说明 |
| --- | --- | --- |
| 预设角色 | `id,name,sex,race,job,level,vipLevel,icon1,icon2,icon3,status` | `clientType` 不属于离线角色长期状态 |
| 位置存档 | 稳定 `mapId,gridX,gridY,updatedAt` | 不保存在线运行时地图 ID `30680` |
| 任务 | `currentMissionId,status,completedMissionIds`，必要时保存目标计数 | NPC 标志优先由任务状态派生 |
| 属性 | `hp,mp,exp,expMax,sp,cp` 和首场战斗必需属性 | 属性 ID 122 名称未确认时不要硬编码错误名字 |
| 经济 | 三类货币当前绝对值 | 结算增量与存档绝对值分开处理 |
| 背包 | `instanceId/templateId,count,position` | 用于任务和战斗奖励持久化 |
| 结算幂等 | `settlementId` 或已结算 ID 集合 | 防止重复提交任务或战斗奖励 |
| 存档元数据 | `schemaVersion,saveRevision` | 支持后续字段迁移和原子写入 |

`seed`、行动计划、心跳 tick、服务器校时时间、其他玩家轮询状态和在线运行时地图 ID 不应作为长期存档字段。

### 10.3 按功能的最小替代

- **创建**：首版直接加载预设角色；若以后保留创建 UI，则由本地服务生成稳定 ID、补全外观并一次性保存，不发网络请求。
- **任务**：接取、提交、奖励、下一主线更新应在同一个本地事务中完成。在线的 `14591` 可替换为事务完成后的本地状态通知。
- **移动**：前端先移动，后端异步接受最新坐标；检查地图边界和可行走格后覆盖保存。无需伪造 `10504` 同号响应。
- **战斗**：客户端可继续本地演算，但后端必须检查当前任务/怪物、初末 HP/MP 合法范围和结算幂等。原校验算法未知时采用明确的临时规则，不能声称复刻原服。
- **切图**：首版拒绝离开首图；后续实现时保存稳定原始地图 ID，并在加载时生成或映射运行态 ID。
- **系统后台**：心跳、世界聊天、战令、其他玩家、等级开放提示均不属于首版必需状态。

## 十一、未确认项和建议补抓

1. 战斗进入 `12501` 的请求、响应和失败分支。
2. `12502` 三轮行动计划的嵌套 bytes 格式、技能参数、seed 规则和服务端校验算法。
3. `12533` 各 int 的精确业务标签及其与 `12502` 的强关联关系。

## 十三、最终分类

按原 H5 首版价值可分为三组；Android 的采用顺序以适配索引为准：

- **首版必须实现**：预设角色加载、首图世界数据、即时移动与位置存档、任务状态和奖励事务、一场本地战斗结算、属性/货币/背包持久化。
- **后续扩展证据已具备**：本地创建角色字段、任务寻路、主线连续推进、运行时/原始地图双 ID、切图数据块框架。
- **首版明确暂缓**：在线心跳与校时、世界聊天、战令、其他玩家轮询、等级开放提示、跨图、原服完整反作弊校验。

当前证据足以设计离线首版的状态和持久化边界，但不足以声称已完整恢复原服的战斗验证、任务奖励长尾、NPC 对话和多人场景协议。
