# 微信小游戏明文协议采集

适用于本机微信小游戏进程。采集只读取运行时明文；原始帧、时间线和摘要必须保存在本项目内。

## 工具

- Frida 和 `frida-ps.exe`：`C:\Users\Administrator\AppData\Local\Programs\Python\Python312\Scripts\`
- 通用采集器：`capture_miniapp_protocol.py`

旧的 `capture_create_role.py` 和 `capture_create_role_flue.py` 只筛选创建角色消息，已由通用采集器取代。通用采集器记录所有可识别的游戏帧，并用 `wechat-miniapp/api-cg-index.csv` 补充协议名。

## 采集

1. 先列出进程，确认实际承载小游戏网络的 PID：

   ```powershell
   & 'C:\Users\Administrator\AppData\Local\Programs\Python\Python312\Scripts\frida-ps.exe'
   ```

2. 默认钩取微信 `flue.dll` 明文边界，显式传入 `--transport flue`。仅在用户明确指定时使用 WinHTTP：

   ```powershell
   & 'C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe' .\capture_miniapp_protocol.py --transport flue --pid <PID>
   ```

   当前实测 RVA 为客户端写 `0x573550`、客户端读 `0x4C06990`。RVA 随微信版本变化；升级后必须重新核对，并通过 `--flue-write-rva`、`--flue-read-rva` 传入新值。

3. 确认 `ready.json` 且双向心跳已写入时间线和原始帧，再通知用户连续操作。只有 ready 或持续零帧时，先检查目标进程、登录连接状态及钩子。等用户确认本轮操作结束后按 Ctrl+C 停止，不按单个操作提前结束。默认产物位于 `captures/miniapp-protocol/session-*/`：

   - `frames/`：按方向和消息号保存的完整二进制游戏帧。
   - `unparsed-payloads/`：不能按游戏帧拆分的明文载荷，可能包含 HTTP、资源或遥测流量。
   - `timeline.jsonl`：帧方向、消息号、长度、SHA-256 和文件名。
   - `transport-events.jsonl`、`ready.json`、`summary.json`：钩子、传输和采集结果。

运行 `python .\capture_miniapp_protocol.py --self-check` 可验证本地拆帧逻辑。分析时先以同一操作的动态明文为证据，再用小游戏逆向代码补齐字段；未动态覆盖的含义标记为“推断”。

### 行动计划后的零字节

本会话 7 份 12502 请求在行动计划之后都有 4 个零字节。此前“未知尾字段”结论已被原代码复现替代：`Message.putBytes` 调用 `putLength` 时按字符串所需的 `2*length+3` 分配数组，却只写入 `length+3` 字节；`ByteArray.bytes` 与 `encodeMsg` 把分配数组全部发送。本轮末条计划长度为 4，因此留下 4 字节缓冲余量。

运行 `node captures/miniapp-protocol/session-20260906-194937/check_serialization.cjs` 可复现；`analyze.py` 已自动调用。脚本仅抽取并执行已有 ByteArray、Message、encodeMsg，7 份请求含帧头全部逐字节匹配，并验证长度为 0/1/4/8 的计划产生相应余量。原始代码与帧哈希、逻辑长度、分配长度保存在 [serialization-check.json](../captures/miniapp-protocol/session-20260906-194937/serialization-check.json)。

不能统一裁去固定 4 字节，也不能将其他协议的尾零一概视作填充。解析器只在对应原帧通过序列化完整重建后标注 `serializationPadding`，保留原字节。本次没有修改原客户端的序列化实现。

## 复用当前登录连接主动请求（2026-09-07）

使用项目根目录的 `request_miniapp_protocol.py`。工具等待当前连接的双向心跳，调用已确认的 `flue.dll` 写入口发送独立 WebSocket 帧，不扩大或改写既有缓冲区。每次请求保存原始请求、响应、SHA-256 和 `requests.jsonl`；输出目录必须在项目内且不能覆盖已有目录。

```powershell
python request_miniapp_protocol.py --self-check
python request_miniapp_protocol.py --pid <PID> world-catalog
python request_miniapp_protocol.py --pid <PID> enter-map <entryId>
python request_miniapp_protocol.py --pid <PID> send <messageType> --payload-hex <HEX>
```

`world-catalog` 只读请求 `10521`，再为每个区域请求 `10522`。`enter-map` 请求 `10523`，会改变角色在线位置；参数是 `10522` 返回的入口 ID，不是原始地图 ID。通用 `send` 只提供传输能力，调用前仍须按静态代码或已保存帧核对请求字段，不能猜测协议。

本次完整目录保存在 [`world-catalog-20260907/result.json`](../captures/miniapp-requests/world-catalog-20260907/result.json)：14 个区域、57 个地图入口、15 组请求响应。44 个入口标记 `isNeedItem=1`，13 个为 `0`；该字段只按服务端原值记录，不能单独证明账号可进入。
